```bash
git lfs install

                                          # route generation return an explicit "run git lfs pull" error.
```

## 3. Environment variables

Create `.env` in the repository root (never commit it):

```
GEMINI_API_KEY=your-key-here
GEMINI_MODEL=gemini-2.5-flash      # optional; this is the default
```

The key is read only by the backend and never sent to the browser. Without a key, everything except
Mars Intelligence and AI trade-off prose still works; those panels say so plainly.

## Final report

**Changed files.** Listed in section 1.

**Two-map synchronisation.** Every selection (coordinate click, USGS feature, custom place, Safe
Haven) calls `/usgs/sync`, which projects the coordinate into the USGS map's own
`Robinson_clon0_Mars_2000_Sphere` (R = 3,396,190 m; verified against PROJ to 0.26 m) and returns a
Web AppBuilder URL with the supported `extent=…,wkt=…` parameter. The iframe is remounted on that URL.
Sync status is derived from state (SYNCHRONISING / SYNCED / SYNC FAILED); failures are shown, never hidden.

**USGS route snapshot.** `/usgs/route-snapshot` stitches MOLA-hillshade tiles from the SIM 3292 web
map's basemap service and overlays geologic units, contacts, structures and landing sites from the
Tanaka et al. 2014 FeatureServer, all in the map's projection. Reports units crossed (fraction of
route), provenance and resolution. Exportable as JSON.

**AI route design.** Deterministic, not generated by a language model: Dijkstra over an 8-connected
grid in a bounded MOLA window (≤120 km), cost families for distance, EVA, terrain, science,
operational and risk; RDP simplification to ≤32 waypoints; duplicates merged at 95 % cell overlap;
Pareto flags. All candidates are drawn at once in matching colours; APPLY ROUTE copies the waypoints
into the existing route editor, so Analyze/Save/Compare/Export work unchanged.

**Scoring methodology.** Objective score = weighted sum of each objective normalised by its own
optimum on the same grid (weights always total 100). Terrain burden = 0.6 slope + 0.4 roughness.
Terrain-risk proxy = 0.35 max slope + 0.25 p90 slope + 0.20 max roughness + 0.10 relief + 0.10 length,
labelled a NeuroNexus derived proxy, not a certification. EVA time = distance / pace + ascent / ascent
allowance (both configurable). Science = fraction of catalogued evidence within its engagement
radius; `None` (UNAVAILABLE), never 0, when no evidence exists.

**Gemini integration.** `google-genai`, server-side, model from `GEMINI_MODEL` (default
`gemini-2.5-flash`). Chat uses manual function calling (≤6 rounds). Route analysis uses a strict JSON
schema (summary, selected_candidate, tradeoffs, evidence, uncertainties, recommendation_basis,
confidence, sources) and may not alter numbers. 404/auth/quota errors are mapped to clear messages.

**Bot tools (18).** selected location, selected feature, environment, terrain analysis, route plan,
route candidates, saved routes, compare routes, rover photos, USGS features, THEMIS context, Mars
weather context, NASA briefing, Safe Havens, custom places, orbital small-body alerts, mission
console state, project provenance. Missing data returns UNAVAILABLE; results are size-bounded.

**CSV fix.** The old export wrote only `routePlan.waypoint_analysis` in 11 fixed columns. Now one
mission object feeds both exports; the CSV flattens every scalar in it into long form
(`record_type, record_id, parent_id, field, value, unit, status, source, source_url, timestamp,
latitude_deg, longitude_deg`), arrays of objects becoming child records. RFC 4180 quoting, CRLF,
UTF-8 BOM. A separate per-waypoint route CSV is kept.

**Dynamic console.** `buildMissionConsoleState()` derives Mission, Crew, Vehicles, EVA, Radiation,
Life Support and Resources from App.jsx state. Every value carries an evidence status and, where one
exists, a NASA/USGS/JPL link. Unmodelled values say NOT MODELED / NOT CONNECTED / NO LIVE FEED instead
of fictional percentages. Mission timeline and life-support are an editable simulation profile.

**JPL tracking.** `/orbital/mars-close-approaches` queries the JPL SSD CAD API with `body=Mars`
(no class filter). Bands: HIGH-PRIORITY (3σ min ≤ 0.0066 au, Mars Hill radius), REVIEW, MONITORING,
LOW-CONCERN, DATA ONLY. UI: log-distance Mars-centred schematic with 3σ bars (no direction implied),
table with SBDB links. Monitoring only; no interception capability.

**Tests run.** Python 54 passed; Node 31 passed. Browser smoke test (Playwright, real backend, real
MOLA tiles): map click → selection → USGS sync → AI Route Designer (6 candidates on real terrain) →
APPLY ROUTE (4 waypoints in the route editor) → USGS SNAPSHOT enabled → USGS map synced; 0 console
errors. Earlier full pass also confirmed orbital tracking (39 live JPL rows), console tabs, graceful
Mars Intelligence without a key, and JSON (69 KB) / complete CSV (322 KB) downloads.

**Build.** `vite build` succeeds (~480 kB JS, ~80 kB CSS). ESLint: all new/changed files clean; the
remaining findings are the ones already present on `Master-Ai` in untouched files.

**Environment variables.** `GEMINI_API_KEY` (required for AI), `GEMINI_MODEL` (optional).

**Known limitations.**
- USGS tile cache stops at level 5 (1,033.5 m/px); smaller snapshots are upsampled and labelled so.
- Snapshots refuse routes that cross ±180° rather than drawing them wrongly.
- Route planning window capped at 120 km; longer traverses need intermediate waypoints (the UI says so).
- The USGS snapshot of very wide extents can take ~40 s on first request (cached afterwards).
- JPL CAD gives no approach direction; the schematic is distance-only.
- `EXPORT ROUTE CSV` does nothing until a route exists.

**Intentionally unavailable (reported, not faked).** MRO CTX, HiRISE, CRISM, SHARAD and Mars 2020
in-situ data are not ingested; no live radiation, weather, dosimeter or biometric feeds; vehicle
power/propellant/comms/thermal are not modelled; rover photos have no coordinates, so they cannot
score routes.
